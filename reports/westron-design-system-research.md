# Share the contract, not the UI code: the architecture of westron

The design decisions of westron should not go into a shared cross-platform UI library. They belong in one platform-neutral, machine-readable source in the repository: tokens in the DTCG 2025.10 format, component contracts and design language documents. From this source, deterministic generators produce native tokens and API "skeletons", that is, the `Variant` and `Size` enumerations and protocols with signatures. Claude Code writes the components themselves natively in SwiftUI, on the web (CSS + Lit) and in GTK4/libadwaita, and then checks them against the contract. Every living multiplatform system works this way (Material, Fluent, Spectrum, Backpack): they share data and algorithms across platforms, but not UI code. Adobe designed native UniFFI/JNI bindings to its Rust data core and never built them. Attempts to compile components from a single description (Lona from Airbnb, Redwood from Cash App) stalled. The strongest argument of 2026: in September Shopify moved from React Native back to native. In its words, agents made implementation on each platform cheaper, and what stayed shared were specifications, tests and review checkpoints. The "identical names" requirement is achievable, but no public system holds it by discipline. Even in Backpack the variant axis is called `style` on iOS and `type` on Android. So names must be generated from the contract: then renaming a value breaks compilation on every platform. Add to the three requirements:
- an explicit "what is native and what is brand" policy;
- a registry of documented divergences;
- a state and accessibility model with platform adapters;
- theme, contrast and density modes;
- catalog apps on every platform;
- CI parity checks;
- an agent context layer generated from the same source.

The best way to work with Claude Code is spec-first with three approval gates. The human approves the contract, the visual matrix and the release. The agent runs the interview, writes the specification, implements the platforms in parallel and checks itself with hooks, tests and a reviewer subagent.

## No living multiplatform system shares UI code, only data

As of November 2026, the large systems are built the same way: one design language, a shared data layer (tokens, component schemas, color algorithms) and a separate native library for each platform. Microsoft Fluent 2 maintains five implementations (React, Web Components, Apple on UIKit/AppKit with SwiftUI integration, Android on Compose, and WinUI) and states directly that **the single language "carries over into each platform library"** ([Fluent 2](https://fluent2.microsoft.design/get-started/develop)). Adobe keeps a platform-neutral monorepo, `spectrum-design-data`: tokens, JSON schemas of components, a vocabulary registry and a data specification. Its registry lists the iOS implementation only as a "proof of concept" ([spectrum-design-data](https://github.com/adobe/spectrum-design-data); [implementation registry](https://github.com/adobe/spectrum-design-data/blob/main/packages/design-data/registry/platform-implementations.json)). Google left iOS back in July 2021, and at I/O 2026 it moved the Views-based Android library into maintenance mode: Material is now "all-in" on Compose ([material-components-ios](https://github.com/material-components/material-components-ios); [material-components-android](https://github.com/material-components/material-components-android)). Across platforms, Google still shares only algorithms: `material-color-utilities` with ports to C++, Dart, Java, Kotlin, Swift and TypeScript ([material-color-utilities](https://github.com/material-foundation/material-color-utilities)). Skyscanner Backpack, the most complete open SwiftUI + Compose pair, is built the same way. Tokens live in the `backpack-foundations` package with `common/base` and `common/app` tiers and platform packages; the native repositories pull them from npm and turn them into code through templates ([backpack-foundations](https://github.com/Skyscanner/backpack-foundations)).

Even well-funded teams are cutting the number of libraries. Kiwi.com archived `orbit-swiftui` and `orbit-compose` in July 2025 ([orbit-swiftui](https://github.com/kiwicom/orbit-swiftui)). Telefónica's native Mística repositories became unavailable ([Telefonica/mistica](https://github.com/Telefonica/mistica)). In August 2026 Skyscanner archived the public web version of Backpack ([Skyscanner/backpack](https://github.com/Skyscanner/backpack)). Adobe archived `spectrum-css` ([spectrum-css](https://github.com/adobe/spectrum-css)), Shopify archived `polaris-react` ([polaris-react-archive](https://github.com/Shopify/polaris-react-archive)), and Material Web is in maintenance mode "pending new maintainers" ([material-web](https://github.com/material-components/material-web)). For a solo developer the conclusion is hard: **no more than one native library per platform** and no parallel wrappers for several web frameworks. Only three living open SwiftUI systems remain to build on: Backpack-SwiftUI, `fluentui-apple` and `mobile-ios-ui` from GOV.UK One Login ([mobile-ios-ui](https://github.com/govuk-one-login/mobile-ios-ui)).

| Architecture | Public examples | What practice shows | Fit for westron |
|---|---|---|---|
| Shared UI runtime | React Native (Shopify, 2020–2026), Compose Multiplatform, Flutter | Shopify returned to native in September 2026; Airbnb did the same in 2018 | Contradicts the native UI requirement |
| Shared non-UI core + native UI | 1Password (Rust Core), Signal (`libsignal`), Telegram (`tdlib`) | The core reaches the UI boundary; the UI is written separately | Fits westron's products, but FFI is overkill for design decisions |
| Neutral specification + native implementations | Spectrum, Backpack, Fluent, Lyft, Spotify Encore | Parity rests on the contract, checks and process | The basis for westron |

Shopify's September post "Back to native" gives this choice the strongest support. For five years the company moved all its apps to React Native and reported screen loads under 500 ms at P75 ([Shopify, 2025](https://shopify.engineering/five-years-of-react-native-at-shopify)). Now it writes: **"LLMs changed one of the key assumptions behind our 2020 decision"**, "agents reduced the payoff of a shared implementation". The Shop app was rebuilt natively in 12 weeks, with agents implementing features on one platform while looking at the other as the reference. The shared mechanism that remained was "shared specs, tests and review checkpoints" ([Shopify Engineering](https://shopify.engineering/back-to-native); [InfoQ](https://www.infoq.com/news/2026/09/shopify-drops-react-native/)). Adobe reached the same conclusion from the other side. Its strategy document says directly that an early option with generated platform SDKs and UniFFI/JNI/FFI bindings **"was never built"**. Instead, the platforms receive a resolved data set and own their code generators themselves ([Spectrum SDK strategy](https://github.com/adobe/spectrum-design-data/blob/main/SPECTRUM_MULTIPLATFORM_SDK_STRATEGY.md)). Generating whole components from a neutral description stalled again and again. Airbnb's Lona got stuck in "Developer Preview" and has not been updated since January 2023 ([Lona](https://github.com/Lona/Lona)). Cash App's Redwood has been marked "no longer under active development" since November 2025 ([Redwood](https://github.com/cashapp/redwood)). Even Diez, which turned TypeScript tokens into native packages, has not been updated since December 2022 ([Diez](https://github.com/diez/diez)). What survived is token generation on open, extensible engines: Style Dictionary released version 5.8.0 in November 2026 ([Style Dictionary](https://github.com/style-dictionary/style-dictionary/releases)).

This answers the open question. **One cross-platform library as a runtime: no. One cross-platform data source with a single version: yes.** Design decisions are stored in the repository as data and split into three layers by how they are produced. Nathan Curtis calls such a source a "contract": it "centralizes design intent in one place", no platform owns it, and **"a description informs, a contract settles disputes"**. Deterministic scripts generate 80–90% of a component's code, agents finish the rest, and regenerating from unchanged input must produce an empty diff ([Curtis, Component Contracts](https://nathanacurtis.substack.com/p/component-contracts-and-schemas)).

| Layer | What it includes | Who produces it |
|---|---|---|
| Generated deterministically | Tokens (color, spacing, radii, text roles, animation) for Swift, CSS, GTK CSS, Rust and later Kotlin; option enumerations and API protocols; snapshot test matrices; documentation and agent context | Scripts in `tools/`; unchanged input gives an empty diff |
| Written natively from the contract | Component bodies, interaction, animation, accessibility, adapting to window size | Claude Code following the platform skill; checked by tests and the reviewer |
| Left to the system | Navigation, toolbars, sheets and dialogs, menus, pickers, text input, scroll physics, focus and keyboard shortcuts, window chrome, the system font for body text | The platform; westron only tints it with tokens |

A shared library has one honest advantage: a single implementation cannot diverge from itself. But the price is nativeness, complex builds for watchOS and GTK, and an FFI bridge. Generated enumerations together with CI checks also deliver the main benefit, parity. A shared core in Rust with UniFFI or Kotlin Multiplatform is justified only for real non-UI logic: validation, formatting, state machines. That is a product core, not a design system. Even if the products' core is in Rust, tokens are better shipped as a generated `consts.rs`, with no runtime bindings.

## DTCG 2025.10 is stable, but the generators for SwiftUI, GTK and Rust are ours to write

The token format is finally stable. The W3C Community Group released **the first stable version, 2025.10, on October 28, 2025**, made of three modules: Format, Color and Resolver ([W3C DTCG](https://www.w3.org/community/design-tokens/2025/10/28/design-tokens-specification-reaches-first-stable-version/)). These are Community Group reports, not a W3C standard ([Resolver 2025.10](https://www.w3.org/community/reports/design-tokens/CG-FINAL-resolver-20251028/)). In 2026 the group only maintained the specification. The draft of September 8, 2026 itself asks not to be implemented, and there is no roadmap for the next version ([DTCG Format draft](https://www.designtokens.org/tr/drafts/format/); [W3C CG](https://www.w3.org/community/design-tokens/)). The format's gaps matter for westron specifically. The `dimension` type allows **only `px` and `rem`**. There is no type for spring animation, although SwiftUI has long built animation on springs ([issue #429](https://github.com/design-tokens/community-group/issues/429)). There are no boolean or string types and no notion of "platform": platform differences are expressed with an ordinary modifier ([Resolver draft](https://www.designtokens.org/tr/drafts/resolver/)). The practical conclusion: DTCG 2025.10 is the canonical format of westron. Everything it lacks (springs, platform mappings, usage rules for the agent) goes into `$extensions` under a key like `dev.westron.*`. Sizes are stored in px, and the generators derive pt, dp, sp and rem.

No ready-made tool covers all of westron's platforms. **Style Dictionary 5.8.0** (November 3, 2026) is the most extensible engine. Out of the box it supports Swift (leaning toward UIKit), Compose `object`, Android XML and CSS. DTCG color objects are supported since version 5.3, dimensions since 5.4, durations since 5.7 ([CHANGELOG](https://github.com/style-dictionary/style-dictionary/blob/main/CHANGELOG.md)). But **the core still has no resolvers**. The team behind Autodesk's Weave design system runs them in production through its own preprocessor of about 180 lines ([issue #1590](https://github.com/style-dictionary/style-dictionary/issues/1590)). Terrazzo 2.10 is built on DTCG and resolvers from the start, but its Swift plugin is experimental and generates only colors, and there is no Kotlin plugin at all ([Terrazzo](https://github.com/terrazzoapp/terrazzo); [Terrazzo Swift](https://terrazzo.app/docs/integrations/swift/)). None of the engines has formats for GTK, QML or Rust ([SD formats](https://styledictionary.com/reference/hooks/formats/predefined/)). Theo is archived, and `fluentui-token-pipeline` was archived back in 2024 ([Theo](https://github.com/salesforce-ux/theo); [fluentui-token-pipeline](https://github.com/microsoft/fluentui-token-pipeline)). Recommendation: **Style Dictionary 5 with custom formats** plus a small resolver preprocessor. (Not adopted: decisions/0004 chose our own generator that reads DTCG directly.) The generators for SwiftUI (`Color`, `Font`, `CGFloat`, colorset), libadwaita `style.css` and `consts.rs` are small template tasks that suit an agent well.

Large systems keep three tiers of tokens. For Material it is `ref → sys → comp` ([material-web tokens](https://github.com/material-components/material-web/tree/main/tokens)), for Primer `base → functional → component` ([Primer token names](https://primer.style/product/primitives/token-names)), for Spectrum 2 about 90 token files by component ([spectrum-design-data tokens](https://github.com/adobe/spectrum-design-data/tree/main/packages/tokens/src)). For a small team the consensus is different: **two authored tiers, primitive tokens and semantic tokens**. Component tokens add indirection that gets in the way of debugging ([Design Systems Collective](https://www.designsystemscollective.com/you-dont-need-all-those-tokens-yet-df9e78a157d2)). Build names with Curtis's grammar (namespace → object → base → modifier): the default mode gets no suffix, and a component-level decision is promoted to a global one only when three or more components need it ([Curtis, Naming Tokens](https://nathanacurtis.substack.com/p/naming-tokens-in-design-systems-9e86c7444676)). A Primer technique is also worth adopting: each token's `$extensions` holds **`usage` and `rules` fields for language models** ("use as the main background… do NOT use for accent"). This directly helps the agent choose a semantic token over a primitive token ([Primer bgColor.json5](https://github.com/primer/primitives/blob/main/src/tokens/functional/color/bgColor.json5)).

```json
{
  "color": { "bg": { "default": {
    "$type": "color",
    "$value": "{color.palette.neutral.50}",
    "$description": "Main background of the window and the page",
    "$extensions": { "dev.westron.usage": {
      "use": ["window-background", "page-background"],
      "avoid": "Do not use for highlights and accents" } }
  } } }
}
```

Modes are described by resolver modifiers: `appearance` (light/dark), `contrast` (standard/high), `platform` (apple-ios, apple-macos, apple-watch, web, gnome, android) and `density`. Modifiers must be orthogonal, that is, they must not touch the same tokens. Then the order of application does not affect the result, as Terrazzo also advises ([Terrazzo resolvers](https://terrazzo.app/docs/guides/resolvers/)). The key detail is which modes are resolved at build time and which at runtime. The `platform` modifier is resolved at build time. Theme and contrast must be shipped into each platform's native switching mechanism. A constant SwiftUI `Color(red:green:blue:)` **has no separate light and dark variants**, unlike a color from an Asset Catalog ([Apple Color.init](https://developer.apple.com/documentation/swiftui/color/init(_:red:green:blue:opacity:))). So on Apple, colors go into a colorset with appearance variants, and the other tokens go into a generated `Tokens.swift`. The symbols Xcode generates for assets have `internal` access level, so the package needs its own `public` accessors through `Bundle.module` ([Apple Forums 734387](https://developer.apple.com/forums/thread/734387)). On the web `light-dark()` fits, Baseline since 2024 ([MDN](https://developer.mozilla.org/en-US/docs/Web/CSS/color_value/light-dark)); in Compose, `ColorScheme` and `CompositionLocal` ([Android](https://developer.android.com/develop/ui/compose/designsystems/custom)). For libadwaita the research notes disagreed, and the more recent data wins. Separate `style-dark.css` and `style-hc.css` files used to be recommended. But libadwaita 1.8 got full media query support, and GNOME 50 **deprecated autoloading these files in favor of a single `style.css` with media queries** ([GNOME 49](https://release.gnome.org/49/developers/); [GNOME 50](https://release.gnome.org/50/developers/)).

Define primitive color tokens in **OKLCH with a `hex` fallback**. Style Dictionary 5.3+ outputs `oklch()` and `color(display-p3 …)` for the web ([CHANGELOG](https://github.com/style-dictionary/style-dictionary/blob/main/CHANGELOG.md)), and GTK understands `var()`, `oklch()` and `color-mix()` since version 4.16 ([GTK CSS](https://docs.gtk.org/gtk4/css-properties.html)). Check contrast in CI **against WCAG 2.x** for every "text/background" pair in every mode. APCA is not part of WCAG 3: as of April 2026 the contrast algorithm for WCAG 3 is "not yet defined", and the standard itself is expected around 2030 ([Adrian Roselli](https://adrianroselli.com/2026/04/wcag3-contrast-as-of-april-2026.html)). Do not fix typography in absolute sizes. It is better to define semantic text roles (`text.body`, `text.title`) and store in each a base size, a line-height multiplier and a mapping to an Apple text style. The generator turns a role into `Font.custom(_:size:relativeTo:)`, which scales with Dynamic Type ([Apple](https://developer.apple.com/documentation/swiftui/font/custom(_:size:relativeto:))). Spacing that must scale is wrapped in `@ScaledMetric` ([Apple ScaledMetric](https://developer.apple.com/documentation/swiftui/scaledmetric)). Springs are stored as groups of numbers in `$extensions`. On Apple they become `Animation.spring(duration:bounce:)` ([Apple](https://developer.apple.com/documentation/swiftui/animation/spring(duration:bounce:blendduration:))); on the web and in GTK, approximations through `linear()` and `cubicBezier` fallbacks. Generated code is committed so that SwiftPM and Gradle builds do not depend on Node, and CI compares it with the output of a fresh generation.

## Identical names do not hold by discipline: generate them from the contract

None of the public systems studied enforces identical parameter names in code across all platforms. Backpack comes closest: the ten button variant values match one to one on iOS and Android. But the axis itself is called `style` in SwiftUI and `type` in Compose. In SwiftUI the variant is set with a modifier method, in Compose with a parameter. `loading` and `enabled` take `Binding<Bool>` in SwiftUI and a plain `Boolean` in Compose. Even the component directories differ: `Radio` versus `radiobutton`, `GraphicPromo` versus `graphicpromotion` ([BPKButton.swift](https://github.com/Skyscanner/backpack-ios/blob/main/Backpack-SwiftUI/Button/Classes/BPKButton.swift); [BpkButton.kt](https://github.com/Skyscanner/backpack-android/blob/main/backpack-compose/src/main/kotlin/net/skyscanner/backpack/compose/button/BpkButton.kt); [backpack-ios](https://github.com/Skyscanner/backpack-ios/tree/main/Backpack-SwiftUI)). In Fluent on iOS the variant is a `ButtonStyle` enumeration of 11 values (`accent`, `outline`, `subtle`, `danger`…), while on Android it is an enumeration of three values, `Button`, `OutlinedButton`, `TextButton`; the sizes are called `ButtonSizeCategory` and `ButtonSize` ([FluentButtonStyle](https://github.com/microsoft/fluentui-apple/blob/HEAD/Sources/FluentUI_iOS/Components/Button/FluentButtonStyle.swift); [Fluent Android Button.kt](https://github.com/microsoft/fluentui-android/blob/HEAD/fluentui_controls/src/main/java/com/microsoft/fluentui/tokenized/controls/Button.kt)). In Orbit even the sets of variants and the API shape differ: on Android each variant is a separate composable function ([Orbit Compose](https://github.com/kiwicom/orbit-compose/blob/main/ui/src/androidMain/kotlin/kiwi/orbit/compose/ui/controls/Button.kt)). The counterexample is Lyft: "for everything we build, a single name is mandatory". Lyft chose "header" over "navigation bar", because on iOS that term means the top bar and on Android the bottom one ([Lyft](https://www.designsystems.com/a-system-built-on-parity-how-to-treat-all-of-your-users-equally/)).

The best open contract model is **`component.schema.json` from Spectrum**. For each component it describes:
- options with default values and constraints between them (`when`/`require`/`severity`);
- slots from a canonical vocabulary;
- anatomy, including parts that are visible only in a certain state;
- states with a trigger type;
- token bindings;
- abstract accessibility (`role`, `intents`, `keyboardIntents`);
- an implementation registry, `implementations[]`.

The contract is validated at three levels (JSON Schema, `SPEC-0xx` graph rules and fixtures), and the CLI exits with code 1 on a mismatch, so it works as a CI gate ([button.json](https://github.com/adobe/spectrum-design-data/blob/main/packages/design-data/components/button.json); [conformance](https://github.com/adobe/spectrum-design-data/blob/main/packages/design-data-spec/conformance/README.md)). But the Spectrum vocabulary leans toward React: `isDisabled`, `isPending`, and the file `Button.tsx` is named as the source of the constraints. Curtis calls this "one side's testimony, not a contract" ([Curtis, Spec-driven UI](https://nathanacurtis.substack.com/p/spec-driven-ui-component-development)). His own format, Spectacular (2026), generates only React and Lit, and the React output is "not intended for production". iOS and Android receive specifications "through factories and platform skills", that is, through agents ([Spectacular](https://github.com/DirectedEdges/spectacular)). Figma Code Connect marked its SwiftUI and Compose parsers as legacy ([Figma](https://developers.figma.com/docs/code-connect)). Bottom line: **no open format generates production components for SwiftUI or Compose**. On native platforms the contract serves as the arbiter, the gate and the support for the agent, but not as compiler input.

For westron this leads to the following scheme: a neutral contract, a table of platform conventions and generation of API skeletons from the contract. Below is an approximate format (an illustration, not a finished standard):

```yaml
# spec/components/button/button.spec.yaml
id: button
status: approved            # draft → approved → stable → deprecated
consumers: [pilot-app]      # no component is created without a real consumer
options:
  variant:  { type: enum, values: [primary, secondary, tertiary, danger], default: secondary }
  size:     { type: enum, values: [s, m, l], default: m }
  disabled: { type: bool, default: false }
  loading:  { type: bool, default: false }
slots: [label, icon]
states: [hover, focus, pressed, disabled, loading]
constraints:
  - { when: { variant: tertiary }, require: { size: [s, m] }, severity: error }
tokens:
  container.background: { primary: color.accent.emphasis, secondary: color.bg.muted }
  container.radius: radius.control
accessibility: { role: button, keyboardIntents: [activate] }
platforms:
  apple:   { strategy: style-on-system-control, base: SwiftUI.Button, watchos: { sizes: [m] } }
  web:     { strategy: custom-element, tag: w-button }
  linux:   { strategy: style-class, base: GtkButton,
             variantMap: { primary: suggested-action, danger: destructive-action } }
  android: { status: planned }
```

```swift
// Generated from button.spec.yaml. Do not edit by hand
public extension WButton {
    enum Variant: String, CaseIterable, Sendable { case primary, secondary, tertiary, danger }
    enum Size: String, CaseIterable, Sendable { case s, m, l }
}
// The protocol pins the signature: if the handwritten WButton does not implement it, the build fails
public protocol WButtonContract {
    init(_ title: LocalizedStringKey, variant: WButton.Variant, size: WButton.Size,
         action: @escaping () -> Void)
}
extension WButton: WButtonContract {}
```

```kotlin
// Generated from button.spec.yaml. Do not edit by hand
enum class ButtonVariant { Primary, Secondary, Tertiary, Danger }
enum class ButtonSize { S, M, L }
// Usage: WButton("Save", variant = Primary, size = M) { save() }
```

The desired call `Button(variant: .primary, size: .m)` runs into three idioms, and each needs one written rule. The first idiom is **the name collision**. An unqualified `Button` conflicts with `SwiftUI.Button` in any file that imports SwiftUI. Fluent hit the same problem and qualifies `SwiftUI.ButtonStyle` by hand ([FluentButtonStyle](https://github.com/microsoft/fluentui-apple/blob/HEAD/Sources/FluentUI_iOS/Components/Button/FluentButtonStyle.swift)). On the web a custom element name must contain a hyphen, hence Spectrum's `swc-button` ([button.json](https://github.com/adobe/spectrum-design-data/blob/main/packages/design-data/components/button.json)). So it makes sense to introduce **one short prefix on all platforms** (`WButton` in Swift and Kotlin, `<w-button>` on the web) and keep the unprefixed name `button` in the contract. The second idiom is **sizes**. On Apple they are called `mini/small/regular/large/extraLarge`, are set with the `controlSize(_:)` modifier and cascade through the environment ([Apple ControlSize](https://developer.apple.com/documentation/swiftui/controlsize)). The values `.s/.m/.l` are a deliberate choice of parity over idiom. It is justified if westron applies it consistently and treats `@Environment(\.controlSize)` as the default value. The third idiom is **the variant mechanism**. A public initializer with parameters from the contract is needed for parity, and inside it, it is better to apply a custom `ButtonStyle` to the system button. That preserves focus, keyboard support, VoiceOver traits and Liquid Glass adaptation. In GTK, variants become CSS classes of the standard widget (`.suggested-action`, `.destructive-action`). libadwaita has no size classes, so sizes will have to be described in westron's own CSS ([libadwaita style classes](https://gnome.pages.gitlab.gnome.org/libadwaita/doc/main/style-classes.html)).

| Contract concept | Swift (SwiftUI) | Kotlin (Compose) | Web (Lit + CSS) | Linux (Rust + GTK4) |
|---|---|---|---|---|
| Component `button` | `WButton` | `WButton` | `<w-button>` | `WButton` on top of `GtkButton` |
| Option `variant` | `variant: .primary` | `variant = Primary` | `variant` attribute and property | `ButtonVariant::Primary` → CSS class |
| Option `size` | `.s/.m/.l` respecting `controlSize` | `S/M/L` | `size="m"` | westron's own CSS |
| Slot `icon` | parameter or `@ViewBuilder` | composable lambda | `<slot name="icon">` | child widget |
| Cascading theme and density | `Environment` | `CompositionLocal` | CSS custom properties | `style.css` and classes |

The state model is also worth taking from Spectrum. States are split by trigger into "prop" and "interaction". Interaction states have a priority (hover 50 < keyboard-focus 60 < down 70), and `disabled` suppresses all interaction states ([state-model.md](https://github.com/adobe/spectrum-design-data/blob/main/packages/design-data-spec/spec/state-model.md)). Abstract accessibility roles map to platform APIs through adapters: `slider` becomes `.adjustable` on iOS, `dismiss` becomes `accessibilityPerformEscape()` ([accessibility-adapters.md](https://github.com/adobe/spectrum-design-data/blob/main/packages/design-data-spec/spec/accessibility-adapters.md)). Describe hover as a state that watchOS and touch iOS simply never enter, not as a variant. Then there is one model for everyone, and only the availability of triggers differs. No system had machine-readable adapters for watchOS (Digital Crown), macOS or GTK/AT-SPI, so westron will have to describe them for the first time.

Parity is checked at four levels, and there is no ready-made framework for it:
- contract validation (JSON Schema and a few rules);
- a lint of each platform's public API against the contract: the Swift symbol graph, the `.api` dump for Kotlin, the Custom Elements Manifest for the web;
- a snapshot matrix that iterates variant × size × state × theme straight from the contract and renders the combinations with swift-snapshot-testing, Playwright `toHaveScreenshot` or Roborazzi ([swift-snapshot-testing](https://github.com/pointfreeco/swift-snapshot-testing); [Playwright](https://playwright.dev/docs/test-snapshots); [Roborazzi](https://github.com/takahirom/roborazzi));
- a generated "component × platform" status matrix.

Pixel equality across platforms is a false goal. Even Spectrum explicitly excludes "pixel parity with every platform implementation" from the goals of its visual format ([component-visuals.md](https://github.com/adobe/spectrum-design-data/blob/main/packages/design-data-spec/spec/component-visuals.md)). Each platform is checked against expectations derived from the tokens, and the human reviews the images side by side. Uber shows that the discipline pays off. According to the company's internal data, Base components give **3 times faster development and 4 times fewer visual parity issues**. Also, the earlier a problem is found, the faster it gets fixed ([Uber](https://www.uber.com/blog/design-system-at-scale/)).

## On every platform the brand lives in the content and the behavior belongs to the system

Platform owners draw the line the same way. Brand is color (with little of it on controls), illustrations, the tone of copy, icon style, the heading font and the surfaces of the content layer. Structure and behavior stay native: navigation, modality, menus, pickers, text input, focus, window chrome and the system font for body text. This matches the most common pattern in the industry: Primer states directly that "Android follows Material, and iOS and iPadOS follow the HIG" ([Primer mobile](https://primer.style/mobile)).

### Apple: one SwiftPM library of styles on top of system controls

One SwiftUI library for iOS, iPadOS, macOS and watchOS is the right choice. But build it as **a set of styles and tokens on top of system components**, not as a replacement for them. At WWDC26 SwiftUI got incremental updates: toolbar control, reordering (on watchOS for the first time), a new Document API, the `@State` macro and `ContentBuilder`. The behavior of the `@State` macro is back-deployed to iOS 17, and `ContentBuilder` works with any minimum deployment target ([WWDC26 SwiftUI](https://developer.apple.com/wwdc26/guides/swiftui/); [session 269](https://nonstrict.eu/wwdcindex/wwdc2026/269/)). Starting with iOS 27, iPhone apps become resizable, and Apple asks apps to adapt by size classes, not by device type. The main constraint is Liquid Glass. Per the HIG it is a functional layer for controls and navigation, and **"don't use Liquid Glass in the content layer"** ([HIG Materials](https://developer.apple.com/design/human-interface-guidelines/materials)). When building with the iOS 27 SDK, the opt-out key `UIDesignRequiresCompatibility` is ignored, although Apple has not announced the date from which that SDK becomes mandatory ([Apple Forums 832543](https://developer.apple.com/forums/thread/832543)). The HIG Branding page, as revised on September 9, 2026, recommends:
- **using the accent color sparingly**;
- carrying the brand into the content layer that scrolls under the glass;
- using the brand font for headings and the system font for body text;
- expressing the brand "through familiar components".

([HIG Branding](https://developer.apple.com/design/human-interface-guidelines/branding))

watchOS requires a deliberately reduced subset: short single-screen interactions, a shallow hierarchy and the Digital Crown for vertical navigation ([HIG watchOS](https://developer.apple.com/design/human-interface-guidelines/designing-for-watchos)). The research found no open SwiftUI system with documented watchOS support. It makes sense to collect the platform token values for Apple (iOS, macOS, watch) in one Swift file with `#if os(...)` branches: this is an inference, not a published practice. Separately: Xcode 27 exports its own SwiftUI agent skills with the `xcrun agent skills export` command, and they can be given to Claude Code as rules ([Apple: agents in Xcode](https://developer.apple.com/documentation/Xcode/extending-and-customizing-agents)).

### Web: tokens in CSS and Lit components on top of native primitives

For a solo developer who needs framework independence, the leanest form is this: CSS custom properties in `@layer` cascade layers plus framework-independent Web Components on Lit. In October 2025 Lit moved from Google to the OpenJS Foundation ([OpenJS](https://openjsf.org/blog/lit-moves-to-openjs-foundation)). The platform already handles much of what systems used to write by hand. `@scope` reached Baseline in December 2025, anchor positioning in January 2026 ([web-features: scope](https://web-platform-dx.github.io/web-features-explorer/features/scope); [MDN position-area](https://developer.mozilla.org/en-US/docs/Web/CSS/position-area)). Dialogs, popovers with `popover="hint"`, style container queries and `contrast-color()` are among the Interop 2026 focus areas ([web.dev Interop 2026](https://web.dev/blog/interop-2026)). The most applicable small-team experience is the post-mortem of the AgnosticUI rewrite. Keeping versions for JSX, Vue and Svelte in sync proved too expensive, and the team moved to Lit on the principle "the platform over the framework". At the same time, `<label for>` does not cross a shadow root, and **full form-associated elements require rewriting validation, reset and value by hand** ([AgnosticUI post-mortem](https://blog.master.dev/post-mortem-rewriting-agnosticui-with-lit-web-components/)). For input fields it is wiser to keep the native `<input>` and `<select>` and style them with CSS. If westron's web products are React-only, it is faster to take Base UI 1.x, which has 35 accessible components ([InfoQ](https://www.infoq.com/news/2026/02/baseui-v1-accessible)), and layer westron's CSS on top, accepting the tie to React.

### Linux: GTK4 and libadwaita in Rust, the brand through the accent

The most defensible native target is GTK4 + libadwaita. GNOME 51 came out on September 16, 2026 and became the default desktop in Ubuntu 26.10 and Fedora 45 ([OMG! Ubuntu](https://www.omgubuntu.co.uk/2026/09/gnome-51-released)). The Rust bindings are mature: `libadwaita` 0.9 works with `gtk4` 0.11, and there is Relm4 0.11 ([docs.rs libadwaita](https://docs.rs/crate/libadwaita/0.9.2); [docs.rs relm4](https://docs.rs/crate/relm4/latest)). If the products' core is written in Rust, the GTK layer needs no FFI. The price is narrow room for the brand. An app can override the accent color through `--accent-bg-color` and `--accent-color` and add a small `style.css`. **High contrast then turns on automatically, and the app "cannot disable it"** ([libadwaita: Styles](https://gnome.pages.gitlab.gnome.org/libadwaita/doc/1-latest/styles-and-appearance.html)). The GNOME HIG asks to keep custom styling "to a minimum" and to use the stock classes and variables ([GNOME HIG](https://developer.gnome.org/hig/guidelines/ui-styling.html)). On Linux, westron is Adwaita with the westron accent, heading typography, icons and illustrations, not a full repaint. The alternatives are weaker. Qt/Kirigami is justified only if the main audience is on KDE: the new StyleKit in Qt 6.11 is still a Technology Preview, and KDE is switching its style engine to Union ([Qt 6.11](https://doc.qt.io/qt-6/whatsnew611.html); [KDE Union](https://mail.kde.org/pipermail/plasma-devel/2026-May/123955.html)). COSMIC Epoch 2 promises a new theme engine ([System76](https://blog.system76.com/post/cosmic-epoch-1-updates)). Adwaita for Swift, with a SwiftUI-style API, is tempting, but one person maintains it ([adwaita-swift](https://codeberg.org/aparoksha/adwaita-swift)). If Linux is secondary for the products, an honest fallback remains: a desktop shell on web technologies with the westron web library. 1Password does this on Mac and Windows, and Spotify in its desktop client ([1Password](https://1password.com/blog/1password-8-the-story-so-far)). Accessibility in GTK is not smooth: at the hackfest before FOSDEM 2026 the developers were "somewhat concerned" about the state of AccessKit, which GTK 4.18 includes only as an option ([GTK blog](https://blog.gtk.org/author/mclasen); [GTK: accessibility update](https://blog.gtk.org/2025/05/12/an-accessibility-update/)).

### Android later: Compose on top of Material3 through CompositionLocal

Google describes three paths: extend `MaterialTheme`, replace its subsystems, or build a fully custom system. For a small team the first or second path is pragmatic. `WestronTheme` wraps `MaterialTheme` through `CompositionLocalProvider`, and the Material color scheme is derived from westron tokens. Then even unwrapped Material components look on-brand and keep their accessibility ([Android: custom design systems](https://developer.android.com/develop/ui/compose/designsystems/custom)). Material3 1.5.0-rc01 came out on November 4, 2026, and in it most M3 Expressive components became stable ([compose-material3](https://developer.android.com/jetpack/androidx/releases/compose-material3)). The experimental Style API from Compose 1.11 may become an analog of SwiftUI's `ButtonStyle` ([Compose April 2026](https://android-developers.googleblog.com/2026/04/jetpack-compose-april-2026-updates.html)). Snapshots go through Roborazzi or AGP 9.5+ test suites: Google no longer supports the separate screenshot testing plugin ([Android Studio](https://developer.android.com/studio/preview/compose-screenshot-testing)). Compose Multiplatform does not fit for UI on iOS, because it contradicts the nativeness requirement.

| Platform | Stack | What westron controls | What is left to the system | Visual check for the agent |
|---|---|---|---|---|
| Apple | SwiftUI, one SwiftPM package | Tokens, styles (`ButtonStyle` etc.), content layer components, the heading font | Liquid Glass, navigation, toolbars, sheets, pickers, Dynamic Type | XcodeBuildMCP or Xcode MCP, catalog app, swift-snapshot-testing |
| Web | CSS custom properties + Lit | Tokens, Web Components, themes | `<dialog>`, popover, native input fields, routing | Playwright, Storybook MCP |
| Linux | GTK4 + libadwaita in Rust | Accent, `style.css` for custom widgets, icons | Adwaita widgets, `AdwNavigationView`, `AdwSidebar`, high contrast | Custom screenshot script (no ready-made tool) |
| Android | Compose + Material3 | `WestronTheme`, component wrappers | System "back" navigation, input fields, pickers | Roborazzi or AGP tests |

Decide on icons and fonts right away. SF Symbols and SF Pro are legally tied to Apple platforms ([Apple Forums](https://developer.apple.com/forums/thread/757407)). So westron needs its own SVG icon master on a single grid, either original or based on Lucide (ISC), Phosphor or Tabler (MIT) ([license overview](https://dev.to/usapopopooon/what-i-didnt-know-about-icon-library-licenses-and-you-might-not-either-30of)). On Apple, SF Symbols remain for standard actions, and domain icons are exported as custom symbols. Body text everywhere uses system fonts; on GNOME since version 48 these are Adwaita Sans and Adwaita Mono ([OMG! Ubuntu](https://www.omgubuntu.co.uk/2025/02/gnome-introduces-new-ui-monospace-adwaita-fonts)). If a brand heading font is needed, it must be under the OFL or a similar license. Google Sans Flex has been distributed under the OFL since November 2025 ([9to5Google](https://9to5google.com/2025/11/18/google-sans-flex-font-available/)).

## Ten additions without which the three requirements will not hold

The user's requirements (a shared language, native libraries with platform specifics, and uniform names) are right. But as stated they describe a goal, not a mechanism. The experience of the systems studied shows which mechanisms hold them in place. By 2022 Spotify had "swung too far toward flexibility" and started redefining its fixed rules ([Spotify Encore](https://designsystems.com/how-spotifys-design-system-goes-beyond-platforms/)). Adobe admitted that its 742-line CSV of iOS overrides is not checked by anything and "silently breaks" when the base updates ([Spectrum SDK strategy](https://github.com/adobe/spectrum-design-data/blob/main/SPECTRUM_MULTIPLATFORM_SDK_STRATEGY.md)). The zeroheight 2026 survey found that **59% of teams build UI bypassing the design system** ([zeroheight](https://zeroheight.com/resources/state-of-ai-in-design-systems/)).

| Addition | What it is | Precedent |
|---|---|---|
| 1. Platform adaptation policy | Chapter `09-platform-adaptation.md` with a "native / brand" table and the rule "system control + style over a custom control" | HIG Branding, GNOME HIG, Android |
| 2. Divergence registry | A `platforms` block in every contract: `supported`, strategy, deviations with a reason. A parity gap without a record counts as a bug | `componentAliases` and `namingExceptions` in Spectrum, `SingleUseColor` at DuckDuckGo, Lyft |
| 3. State and accessibility model | Canonical states with priorities; roles and intents with adapters for VoiceOver, ARIA, AT-SPI, TalkBack; Digital Crown; minimum touch target sizes | Spectrum state-model and accessibility-adapters |
| 4. Modes as axes | `appearance`, `contrast`, `density`, `platform`; respecting Reduce Motion and Reduce Transparency, Dynamic Type | Primer: `condensed/normal/spacious` |
| 5. API skeleton generation and parity lint | Enumerations and protocols from the contract; comparing the public API with the contract in CI | Curtis, Spectrum CLI |
| 6. A catalog app on every platform | Isolated rendering of any component: a review surface for the human and a source of screenshots for the agent | Grindr, Spectrum `platform-capture` |
| 7. Agent context layer | Skills, `llms.txt`, a short DESIGN.md and later MCP, all generated from the same source | Atlassian, Primer `org.primer.llm` |
| 8. Decision log and a single version | ADRs next to the contracts and in `decisions/`; one semver version per repository; a machine-readable CHANGELOG with migration sections | Backpack `decisions/`, SwiftPM constraint |
| 9. Pilot product and the `consumers` field | A new component appears only for a real product need | Dan Mall |
| 10. Rules for consumer repositories | A rule in the product's CLAUDE.md, "UI only from westron", plus a "no raw values" lint | zeroheight: 59% bypass |

Three items deserve explanation. The `density` mode is not decoration but a direct consequence of the word "technical" in the description of the products. Dense tables, logs and monospaced text need a compact mode. Set it at the theme or environment level, not as an option of every component. Primer keeps such density scales in token names ([Primer token names](https://primer.style/product/primitives/token-names)), and SwiftUI cascades `controlSize` through the environment. Item 2 is needed because Backpack already lives with components that exist on only one platform (`fab` and `bottomnav` on Android, `CarouselCard` and `Shaders` on iOS) ([backpack-android](https://github.com/Skyscanner/backpack-android)). Lyft says directly about its sheet: "here we chose parity with the platform, not with the design system" ([Lyft](https://www.designsystems.com/a-system-built-on-parity-how-to-treat-all-of-your-users-equally/)). Item 8 is dictated by SwiftPM: a remote package requires `Package.swift` at the repository root, and versions come from repository-level tags. So in a monorepo it is simplest to ship **one version for everything** ([Swift Forums](https://forums.swift.org/t/allow-package-swift-to-not-be-at-the-root-of-the-repository/60431)).

## Work plan: an end-to-end Button slice on three platforms before the twentieth component

The main risk for one person with an agent is not a slow start but premature abstraction. An agent will gladly generate forty components, and systems "fail when they try to do too much too soon" ([Measured](https://dev.to/measuredco/why-design-systems-fail-3ii)). So the plan is built around two anchors. The first is **a real pilot product**: if a suitable product already exists, extract components from it rather than invent them ([Dan Mall](https://danmall.com/posts/design-systems-pilots-scorecards)). The second is **an end-to-end Button slice** on Apple, the web and Linux right after the tokens. A button tests the whole pipeline: tokens, contract, generators, parity lint, snapshots and accessibility. Curtis also warns that styling a button can "overturn many token decisions" made earlier ([Design Systems Collective](https://www.designsystemscollective.com/the-first-component-debate-micro-frontends-ai-in-design-503170b6c139)). The timelines below are rough: the research found no published "one person plus an agent" case with measured timelines.

| Phase | Estimate | Key artifacts | Exit criterion |
|---|---|---|---|
| 0. Scaffold | ≈1 week | A monorepo with `Package.swift` at the root; `CLAUDE.md` and `AGENTS.md`; skills, subagents, hooks; CI; empty catalog apps in SwiftUI, on the web and in GTK; the pilot product chosen | CI is green on three platforms with an empty component |
| 1. Language and tokens | ≈2–3 weeks | Chapters `design-language/00–09`; DTCG tokens in two tiers; a resolver (appearance × contrast × density × platform); generators for colorset + `Tokens.swift`, CSS, `style.css` for libadwaita, `consts.rs`; a contrast matrix in CI; decisions on icons and fonts; an ADR for every foundation | All "text/background" pairs pass WCAG 2 in all modes; the catalogs show token samples |
| 2. Contract and end-to-end slice | ≈2–4 weeks | The contract JSON Schema and rules; the conventions table; a generator of enumerations and protocols; an API parity lint; `Button` on three platforms with snapshots and an accessibility audit | Renaming a value in the contract breaks the build everywhere; the screenshot matrix is built automatically |
| 3. Primitives and forms | as the pilot needs | Text, Icon, Stack/Surface, Divider, TextField, Toggle, Checkbox, Radio, on Apple and in GTK as styles of system controls | Each primitive has passed the three approval gates |
| 4. Pilot components | as the pilot needs | 10–15 components: Select/Menu, Tabs/Segmented, ListRow, Card, Dialog, Sheet/Popover, Toast/Banner, Progress, Badge, Tooltip, Toolbar, SearchField, EmptyState; dense components for technical products | Each has the `consumers` field filled in; the status matrix is green |
| 5. Patterns, documentation, agent layer | as needed | Patterns for forms, errors, empty and loading states, settings; DocC, a static site or Storybook; `llms.txt`; a generated DESIGN.md; a local MCP once there are many components | Documentation and agent context are generated and checked in CI |
| 6. Android | after stabilization | A Compose library on top of Material3 through `CompositionLocal`; a showcase app; Roborazzi | The port follows the finished contracts with almost no changes to them |

```
westron/
  Package.swift              # SwiftPM manifest at the root; targets point into platforms/apple/
  CLAUDE.md  AGENTS.md       # CLAUDE.md starts with @AGENTS.md
  .claude/{skills,agents,rules,settings.json}
  design-language/           # 00-principles … 09-platform-adaptation
  decisions/                 # foundation-level ADRs
  tokens/                    # *.tokens.json (DTCG 2025.10) + westron.resolver.json
  spec/components/<name>/    # <name>.spec.yaml, decisions/, reference screenshots
  platforms/apple/           # WestronTokens (generated), WestronUI, Catalog, Tests
  platforms/web/             # npm package(s), gallery, Playwright
  platforms/linux/           # Rust crate on gtk4-rs/libadwaita, demo app
  platforms/android/         # later: Compose, showcase, Roborazzi
  tools/                     # token and API generators, parity lint, matrix rendering, llms.txt/DESIGN.md generators
```

The order of phases 1 and 2 matters more than their duration. Until the parity lint and enumeration generation work on Button, the second component does not start. Otherwise drift between platforms will appear before the mechanism that is meant to catch it.

## Spec-first with three approval gates is the best way to work with Claude Code

The 2026 measurements agree on one thing: the quality of an agent's work is determined by **structured context loaded on demand**, not by the volume of prose. Atlassian compared context strategies on a "login screen" task. With an MCP server the agent spent on average 3.75 million tokens and 35 turns. With a single DESIGN.md file it spent **7.21 million tokens and 45 turns**, worse than with no context at all. The variance between runs also grew about 2.7 times, and the agent tried to rewrite components instead of importing them. Atlassian itself calls the results "not conclusive" ([Atlassian, DESIGN.md](https://www.atlassian.com/blog/how-we-build/atlassians-design-md-is-here-what-we-learned-testing-portable-design-context-in-practice)). Turning documentation into schemas from which the MCP, the skill and DESIGN.md are generated gave up to a 52% accuracy gain on individual queries. The same source states the lesson: "documentation that has drifted from the code is worse than no documentation" ([Atlassian](https://www.atlassian.com/blog/ai-at-work/teaching-ai-to-speak-our-design-language)). With Code Connect, Figma got **−19.6% time and −29.5% tokens** per task. Component coverage turned out to be the deciding factor ([Figma](https://figma.com/blog/the-benefits-of-code-connect-in-mcp)). In the zeroheight survey, 82% of teams use AI and 74% use Claude. AI does best in documentation and worst in design generation: −53 in net satisfaction ([zeroheight](https://zeroheight.com/resources/state-of-ai-in-design-systems/)).

| Option | What it looks like | Role of the human | Setup cost | Main risk | Verdict |
|---|---|---|---|---|---|
| A. On-demand assistant | Tasks are stated in chat, the agent writes code | Decides everything in the conversation | Minimal | Decisions stay in the chat history, platforms diverge | Only for one-off tasks |
| B. Spec-first with approval gates | Interview → contract → parallel implementation → gates → visual matrix | Approves the contract, the visual result and the release | Medium: skills, hooks, subagents | Contract bloat | **The main mode** |
| C. Formal SDD framework | Spec Kit or Kiro: constitution → specify → plan → tasks → implement | Reviewer of every artifact | Medium or high | Excessive ceremony for one person | Take the constitution idea, but not the whole process |
| D. Canvas first | Claude Design, Penpot or Figma → handoff to Claude Code | Designer on the canvas | Medium; Code Connect is costly to maintain | The canvas becomes a second source of truth; no export to SwiftUI and GTK | Only for exploring directions |
| E. Autonomous pipeline | The agent runs a task queue, the human only looks at PRs | PR reviewer | High, needs mature gates | Volume nobody has reviewed | For later phases: Android port, maintenance |

The recommended mode is **B as the base, D for exploration, and a gradual move to E** once the gates mature. It rests on Claude Code's own recipe. First the agent interviews the human "until it can write a specification". Implementation happens in a fresh session. Then a subagent checks the diff against the specification and verifies that every requirement is implemented and covered by tests ([Claude Code best practices](https://code.claude.com/docs/en/best-practices)). Spec Kit remains a very active project ([Spec Kit](https://github.com/github/spec-kit)), but its full ceremony is designed for teams. For one person, what Claude Code provides out of the box is enough; this is an estimate, not a measured fact. The canvas is useful for finding a direction, but not as a source of truth. Claude Design is now one of the artifact templates, is available in Claude Code and imports a design system from code with the `/design-sync` command. But it **has no version history**, and it has no announced export to SwiftUI or GTK either ([Claude Help Center](https://support.claude.com/en/articles/14604416-get-started-with-claude-design)). So any decision found on the canvas returns to the repository as a contract edit and a reference screenshot. TJ Pitre proposes the same division of roles: the human sets the constraints, AI works within them. Every shipped change has a verifiable trail of a human decision ([Southleft](https://southleft.substack.com/p/context-based-design-systems-revisited)).

The cycle of one component in mode B passes three approval gates.

The first is the interview. The `/new-component` skill asks the human about purpose, scenarios, variants, states and accessibility. Then it writes a draft contract and a short ADR with the options considered. If needed, the agent makes 2–3 HTML sketches on westron tokens. **The human approves the contract**: this is the first approval gate.

The second is implementation. Implementer subagents with `isolation: worktree` write the Apple, web and Linux versions in parallel in separate git worktrees and add entries to the catalogs and snapshot tests ([Claude Code subagents](https://code.claude.com/docs/en/sub-agents)). A `Stop` hook with exit code 2 keeps the agent from declaring the work finished until the tests of the affected packages pass ([Claude Code hooks](https://code.claude.com/docs/en/hooks)). The `spec-reviewer` subagent with fresh context checks each requirement against the list, and `a11y-auditor` runs `performAccessibilityAudit` and axe. CI builds an image matrix: rows are states, columns are platform × theme × font size. **The human looks at the matrix and the snapshot diff**: the second approval gate. If a gap turns up, the contract is fixed first and only then the code. The contract always outranks any reference implementation. It is convenient to implement a component first on the platform the pilot needs earliest and give it to the others as the reference, as Shopify did.

The third is the release. Only the human can invoke the `/release` skill with the `disable-model-invocation: true` flag ([Claude Code skills](https://code.claude.com/docs/en/skills)). This is **the third approval gate**. At all three gates a rule from the Claude Code documentation applies: ask for evidence (a command that was run, with its output, or a screenshot), not the phrase "tests passed".

| Claude Code mechanism | What to put there | Why |
|---|---|---|
| `CLAUDE.md` (under 200 lines, first line `@AGENTS.md`) | Build, test and snapshot commands per platform; the rule "no raw values, tokens only"; links to the design language chapters | Persistent context; anything that must always happen is made a hook, not text |
| `.claude/rules/*.md` with `paths:` | SwiftUI rules for `platforms/apple/**`, Lit/CSS for `platforms/web/**`, GTK for `platforms/linux/**` | Loaded only when working in the matching folder |
| Skills | `/new-component`, `/implement-platform <component> <platform>`, `/visual-check`, `/release`, a background design language skill generated from `design-language/` | Procedures loaded on demand |
| Subagents | `spec-reviewer`, `a11y-auditor`, one implementer per platform with `isolation: worktree` | Fresh context for review, parallel platforms |
| Hooks | `PostToolUse` on `Edit`/`Write`: token lint and formatter; `Stop`: tests and snapshots of the affected packages | Deterministic gates |
| Visual loop | XcodeBuildMCP or Xcode MCP for the simulator and previews; Playwright for the web; a custom screenshot script for the GTK catalog | The agent sees the result of its work |

The weakest spot in this scheme is the agent's vision. Grindr stated the problem plainly: **"Claude can't see Xcode Previews and builds SwiftUI components blind"**. Its solution is a CLI that spins up a minimal app for one component and runs it in the simulator ([Grindr](https://www.grindr.com/blog/claude-cant-see-xcode-previews----heres-how-we-fixed-it)). XcodeBuildMCP adds building, screenshots and reading the accessibility tree, but so far it is described only in secondary sources ([mcp.directory](https://mcp.directory/blog/xcodebuildmcp-complete-guide-2026)). For GTK, no ready "screenshot and accessibility audit" loop was found at all. So the catalog apps from phase 0 are not decoration but infrastructure: they pay off twice, as a review surface for the human and as the agent's eyes.

## Conclusion

The economics of multiplatform systems has flipped. In 2018–2023 writing N implementations was expensive, so the industry tried either to share the runtime or to compile one description into many languages. Both strategies retreated: Shopify returned to native, Lona and Redwood stalled. In 2026 agents made implementation cheap, and now the most expensive parts are a precise contract and checking conformance to it. So the main product of westron is not three libraries but the contract, the generators and the gates, from which the libraries come out as projections. This sets the order of investment: first the contract schema, the conventions table, the parity lint and the catalogs, and the number of components later. Then uniform names become a property the compiler checks, not a promise that rests on attentiveness.

The second conclusion concerns identity. There is less room for the brand on native platforms than it seems. Apple moves the brand into the content layer under the glass, GNOME leaves mostly the accent color, Android suggests wrapping Material. The recognizability of westron will not live in repainted buttons and navigation. Its sources are content layer components for technical tasks (dense tables, code, statuses, empty states), the heading font, domain icons, the tone of copy and the density mode. Record this decision as the first principle in `00-principles.md`. Three questions remain open, and they must be closed in phases 0–2. Who is the Linux audience: GNOME, KDE, or is a web shell acceptable? Should `.s/.m/.l` be adopted against the Apple idiom? How to compensate for the lack of snapshot and accessibility audit tools for GTK? Also, there is no published case of "one person and an agent build a multiplatform system"; westron will be one of the first.
