# 0004. Data source formats

Date: 2026-11-14. Status: accepted.

## Decision

| What | Format |
|---|---|
| Tokens (color, spacing, radii, typography, animation) | DTCG 2025.10, `*.tokens.json` files |
| Modes (theme, contrast, density, platform) | DTCG resolver, JSON |
| Component contracts | Our own YAML, validated by JSON Schema |
| Design language and decisions | Markdown |

## Details

- We do not introduce our own token format. DTCG gives a ready schema (types, aliases, groups, composite tokens, color spaces) with official JSON Schemas, agents already know it, and Figma and the existing engines read it, so they can be plugged in later without migrating the sources.
- Everything DTCG lacks (spring animation, platform mappings, usage rules for the agent) is stored in `$extensions` under the `dev.westron.*` key.
- Sizes are stored in px; the generators derive pt, dp, sp and rem.
- Tokens have two levels: primitive tokens and semantic tokens. A component level is added only when needed.
- "Styles" are not described in a separate format: they are bindings of tokens to variants and states inside the component contract.
- A component contract describes options, states, slots, constraints, token bindings, accessibility, and a `platforms` block with the differences between platforms. The schema is based on `component.schema.json` from Spectrum.
- Tokens are generated by our own generator in `tools/`, which reads the DTCG files and the resolver directly. There is no third-party engine.
- The generator supports only the subset of DTCG that westron uses. The token files are validated against the official JSON Schemas, and the supported subset is listed explicitly next to the generator.
- Color conversion comes from a library, not from our own code.

## Why not Style Dictionary

The research report recommends Style Dictionary 5 with custom formats. We do not follow that recommendation, because nearly everything westron needs from the engine would be our own code anyway:

- Style Dictionary's core has no resolver, so modes need our own preprocessor.
- Its built-in Swift formats lean toward UIKit, so SwiftUI output needs our own formats.
- It does not understand what we keep in `$extensions` (springs, platform mappings), so those need our own transforms.
- It does not generate code from component contracts, so `tools/generate` exists either way and there would be two pipelines.

What remains is file parsing and alias resolution, which is small for the subset we use. The cost is that DTCG edge cases (`$extends`, `$root`, aliases inside composite tokens) become ours to handle; schema validation and the explicit subset list contain it.

The sources stay DTCG, so a third-party engine can still be added for a single platform where it is strong, such as Style Dictionary for CSS on the web (#39).
