# 0017. WestronContract: the contracts' option enums in a module with no imports

Date: 2026-11-24. Status: accepted by the owner on 2026-11-24 (#162).

## Context

When a product moves a screen to westron, sizes, colors and fonts leave the product's models: westron's tokens and
components carry them. What stays in a model is content, actions and the parameters westron's components let a caller
set: a variant, a size, a state, an icon, a nesting level, a list's category. In the pilot, todo-app, those models live
in shared code that cannot import SwiftUI and builds for WebAssembly and Linux as well (decisions/0006).

Part of that vocabulary already had such a home. `Westron.Icon` and `Westron.Category` are in `WestronTokens`, which
imports nothing, not even Foundation (decisions/0010, 0011). The rest did not: the option enums the contracts give
(`ButtonVariant`, `ButtonSize`, `ChipVariant`, `CheckboxVariant`, `TextFieldVariant`, `TextFieldSize`,
`SurfaceVariant`, `RuleAxis`, `RulePurpose`, `ListRowInsertionEdge`, `DisclosureVariant`) were generated into
`WestronUI/Generated/<Component>+Contract.swift`, beside their SwiftUI extensions, in files that import SwiftUI. A model
could name a list's icon and color but not the variant of the button it shows.

The question came up while planning the check of #37 (pull request #164) on todo-app's "Move to…" picker, whose models
are the first to keep westron's vocabulary.

## Decision

The owner, 2026-11-24:

1. **A separate module, `WestronContract`.** A target and a product of the root package, its sources in
   `platforms/apple/Sources/WestronContract/`. It holds every option enum the contracts give, an option's or a mark's
   parameter's, with its doc comment, `String` raw values, `CaseIterable` and `Sendable`, generated by
   `tools/westron generate` into `Generated/<Component>+Contract.swift` from the approved contracts. It imports
   nothing, not even Foundation, as `WestronTokens`, so it builds wherever a product's shared code does. Nothing in it
   is written by hand but a comment.
2. **What stays in `WestronUI`.** Everything that needs SwiftUI, generated into `WestronUI/Generated/` as before: the
   style-modifier overloads, the extensions of the enums (the size a `controlSize` gives, `offered`), the states
   (`ButtonState`, internal) and the forms (`ListRowForm`, `package`). An own component whose contract gives enums alone
   (Rule, Surface) has no generated file in `WestronUI` any more.
3. **`WestronUI` re-exports it.** `WestronUI` depends on `WestronContract` and re-exports it with
   `@_exported import WestronContract` in `WestronUI.swift`, as it already re-exports `WestronTokens`: product view code
   that imports `WestronUI` alone compiles unchanged. The generated files of `WestronUI` name the module in an import
   of their own, so that each says where its types come from.
4. **Models keep westron's vocabulary and lose raw values.** A product's model in shared code names the option enums of
   `WestronContract` and `Westron.Icon` and `Westron.Category` of `WestronTokens`, and holds no size, color, font,
   radius, spacing or duration. A view passes that vocabulary to westron's API and does not turn a product's own value
   into a raw color or size (no `switch` from a model's value to a color). Where a view derives a westron parameter
   from the product's state, it derives one of westron's values, as compositions in decisions/0014 do.
5. **The API parity lint reads both modules.** An enum a contract gives must be declared in `WestronContract`, not in
   `WestronUI`; `WestronContract` declares nothing else, at any access, and imports nothing
   (`tools/westron lint api-parity`, `APIParity.check(…, contractRoot:)`).

Three placements were considered. Into `WestronTokens`: one module for shared code, but tokens are values and a
contract is the vocabulary of options, so the owner kept them apart. One module without UI that takes both, under a new
name: the owner chose against it; a rename would also change the import of every product's shared code that uses
`WestronTokens` today. A new module named after what it holds, the contracts' vocabulary: chosen. westron then gives
clients a UI module and a module of the contracts' vocabulary, beside the token values.

## Consequences

- A product's shared code adds the product `WestronContract`, and `WestronTokens` where it names an icon or a list
  color; its views keep `import WestronUI`. A call site that qualified an enum by its module, `WestronUI.ButtonVariant`,
  still compiles in a file that imports `WestronUI` alone, since the re-export makes the enum visible through it. What
  changes is the module in reflected and mangled names: `String(reflecting: ButtonVariant.primary)` starts with
  `WestronContract.` now, not `WestronUI.`, so code or stored data that keyed on such a name sees a new one.
- `tools/westron generate` writes one or two files per contract and owns both `Generated/` directories, so a file it no
  longer writes in either is stale and `generate --check` fails.
- An enum a future contract gives lands in `WestronContract` by construction, and the lint fails a hand-written one in
  `WestronUI`.
- The agent context's cards (decisions/0016) list a component's enums under `WestronContract`, and the skill tells a
  product's agent what a model keeps.
- `tools/apple/audit-scope.sh` reads `WestronContract` with `WestronUI`: its enums tell a component's style modifier
  from the system's, so a change to one generated file of a component still audits that component's entries.

### Open points

1. **`DisclosureVariant` on watchOS.** SwiftUI has no `DisclosureGroup` on watchOS, so Disclosure does not exist there
   (its contract's `platforms` block), and its API in `WestronUI` stands under `#if !os(watchOS)`. In a module with no
   SwiftUI the reason does not hold by itself: nothing stops `DisclosureVariant` from compiling on watchOS. It stays
   under the same `#if !os(watchOS)` in `WestronContract`, so the vocabulary has the availability the contract records,
   and two checks hold it there: the lint reports an enum in `WestronContract` of a contract with such a condition
   that stands under no `#if` or under another one, and `generate --check` reports any edit of the generated file.
   The cost: shared code that builds for watchOS cannot name it outside the same condition. Whether the vocabulary
   should exist on every OS, so that a shared model may name a disclosure's variant that the watch never draws, is the
   owner's to decide; the change would be the generator's condition and the lint's rule, not a contract.
2. **One import for shared code.** `WestronContract` does not depend on `WestronTokens`, so shared code that names an
   icon and a variant imports both. Whether `WestronContract` should re-export `WestronTokens` is open; it would tie
   the vocabulary's module to the token values.
3. **States in a model.** The states stay `WestronUI`'s: a model keeps a state such as `selected` as the `Bool` its
   modifier takes. If shared code ever needs a state's name, that is a change to this decision.
4. **The Stop hook.** Closed on 2026-11-24. `.claude/hooks/stop-checks.sh` selects its checks by path, and it did not
   name `WestronContract`: a change to the module alone ran the package checks but not `generate --check` or the lint.
   It names the module beside `WestronUI` now, so such a change also runs `generate --check`, the lint, the tools'
   tests and the step audit-scope.
