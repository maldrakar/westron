# Multi-platform design system architecture (Apple, web, Android, desktop/Linux): state as of Nov 2026

Research date: 2026-11-14. Repo facts (archived status, last push dates, directory layouts, enum names) were checked directly against the GitHub API on that date unless stated otherwise. Items from older blog posts carry their year. "(old)" means the information is from before 2024 and may be stale.

---

## Q1. How do the major systems split "one design language" from "per-platform libraries", and which ship real native libraries?

### Takeaway
Almost every large system now uses the same model: one shared design language plus a shared token/data layer, then separate native libraries per platform, each in its own repo or package, owned by platform engineers. No large system shares UI code across iOS, Android and web. By late 2026 only a few public systems still ship open-source native Apple and Android libraries: Microsoft Fluent (UIKit/AppKit/SwiftUI and Android/Compose), Skyscanner Backpack (SwiftUI and Compose) and GOV.UK One Login (iOS and Android). Material dropped iOS in 2021 and is now Compose-first on Android. Several others (Orbit native, Mistica native, Primer mobile, Backpack web) have closed or archived their native and secondary repos.

### Cited Findings

- MDC-iOS and its Material Foundation/Motion dependencies went into maintenance mode on July 15, 2021. Google has no Material library for iOS or SwiftUI. — [material-components-ios README](https://github.com/material-components/material-components-ios)
- At Google I/O 2026 Material Android said it is "all-in" on Compose. The Views-based MDC-Android library "is now in maintenance mode" with "no more planned feature releases for Views". The repo description now reads "[MAINTENANCE MODE]". — [material-components-android README](https://github.com/material-components/material-components-android); [Android Compose-first blog, May 2026](https://android-developers.googleblog.com/2026/05/android-ui-development-is-compose-first.html)
- Material Web (`@material/web`, Lit web components) says "MWC is in maintenance mode pending new maintainers". — [material-web README](https://github.com/material-components/material-web)
- Flutter moved Material and Cupertino out of the core framework. In-framework contributions were frozen on April 7, 2026, and both libraries now ship as standalone `material_ui` and `cupertino_ui` packages (1.0.0 mirrors framework code), developed in flutter/packages. — [Flutter blog: code freeze](https://flutter.dev/blog/flutters-material-and-cupertino-code-freeze); [Flutter blog: decoupling](https://flutter.dev/blog/decoupling-material-cupertino); [Flutter migration guide](https://docs.flutter.dev/release/breaking-changes/material-ui-and-cupertino-ui)

**Adobe Spectrum / Spectrum 2**
- `adobe/spectrum-design-data` (formerly `spectrum-tokens`, which now only redirects) is the platform-neutral monorepo. ### Inferences
- The split that has held up is: design language plus tokens/data shared, components native per platform. Google, Microsoft and Adobe all keep the cross-platform layer to data and algorithms (tokens, color utilities, schemas), never UI code.
- Large vendors are cutting library count. Google is down to Compose for Android plus a community-maintained web library, Material on Flutter is moving out of the framework, Shopify collapsed onto web components and Adobe archived spectrum-css. A one-developer team should expect to maintain one native library per platform at most and should avoid multiple web framework bindings.
- No major open system offers a Linux-native toolkit (GTK/Qt). The only nearby examples are Fluent (WinUI for Windows, AppKit for macOS) and Spectrum's experimental Rust "Rune". For Linux, westron will probably have to rely on web tech (a web-tech desktop shell, as Spotify's desktop client does under Encore Web) or a Rust/GTK binding of its own.

### Gaps
- Airbnb DLS, Lyft (LPL) and Uber Base mobile have no current public docs for native libraries. Their structure is known only from pre-2023 talks and posts, which I did not re-verify.
- Microsoft does not publicly explain why `fluentui-token-pipeline` was archived or what replaced it.
- I did not get the text of the "Material is Compose-first" blog post (the fetch returned only the heading). Facts above come from the MDC-Android README that links to it.
- I could not confirm whether M3 Expressive has official Flutter support.

## Q2. Which systems enforce identical component and prop names across platforms, and how?

### Takeaway
None of the public systems I checked enforces identical prop names across platforms in code. The most rigorous approach is Adobe's: a machine-readable, platform-neutral component and token dataset (JSON Schema, a naming registry, a normative taxonomy) plus per-platform manifests that declare aliases and naming exceptions, validated in CI. Backpack and Orbit, the best-maintained open SwiftUI/Compose systems, show real naming drift even for Button.

### Cited Findings

**Adobe Spectrum: schema and registry as the contract**
- The token taxonomy is NORMATIVE and shared across platforms. Vocabulary and formatting may vary per platform, and platforms declare vocabulary mappings in their manifests. — [Spectrum Design Data: taxonomy](https://opensource.adobe.com/spectrum-design-data/spec/taxonomy/)
- The registry holds the allowed vocabulary for token name fields and component metadata, including anatomy terms such as `label`, `icon` and `track`. — [Spectrum Design Data: registry](https://opensource.adobe.com/spectrum-design-data/spec/registry/)
- Platform manifest fields: `specVersion`, `foundationVersion` (pin), `platform`, `include`/`exclude` query filters, `overrides` (may change only `value` or `$ref`, keep the token key and `uuid`, and never change the resolved type), `namingExceptions {add, remove}`, `formatting {conceptOrder, casing, delimiter, abbreviations, prefix}`, `componentAliases` (e.g. `"button": "button-ios"`) and `modeSetRestrictions`. The `extensions/implementations/` directory maps a component to each platform's package and exported name (example row: `platform: "web"`, `componentName: "Button"`, `package: "@react-spectrum/s2"`). The cascade is `Foundation < Platform < Product`, and Layer-1 schemas cannot be overridden. — [Spectrum Design Data: manifest spec](https://opensource.adobe.com/spectrum-design-data/spec/manifest)
- The real `platforms/ios/manifest.json` pins `"foundationVersion": "3.6.0"`, excludes `colorScheme=wireframe`, sets `"componentAliases": {"button": "button-ios", "switch": "switch-ios"}`, overrides 3 token UUIDs to `rgba(9, 144, 120, 1.0)`, uses `"formatting": {"casing": "camelCase"}` and adds naming exceptions such as `switch-selected-emphasized-track-color`. — [platforms/ios/manifest.json](https://github.com/adobe/spectrum-design-data/blob/main/platforms/ios/manifest.json)
- Validation rules live in `packages/design-data-spec/rules/rules.yaml` (e.g. SPEC-039 manifest-query-parseable, SPEC-041 mode-set-restriction-coverage). `validate`, `validate-dataset` and `diff` exit 1 on drift, so CI can gate on them. A planned reusable GitHub Action will run a "foundation-drift `diff`" of the pinned version against the latest tag on every platform PR. — [SDK strategy doc](https://github.com/adobe/spectrum-design-data/blob/main/SPECTRUM_MULTIPLATFORM_SDK_STRATEGY.md)
- The MCP server `@adobe/spectrum-design-data-mcp` can "validate component props" and look up tokens by use case. A separate `@adobe/s2-docs-mcp` serves S2 component docs. — [Spectrum Design Data: AI](https://opensource.adobe.com/spectrum-design-data/ai)
- Naming policy: "We aim for shared terminology by default, but deviation (different terminology) can be acceptable … different terminology for platform-specific concepts is expected." Also "Things need to *feel* the same across platforms. But not everything needs to *look* the same," and "All UI code and components don't have to be shared across platforms." — [SPECTRUM_NAMING_GUIDE_WIKI.md](https://github.com/adobe/spectrum-design-data/blob/main/SPECTRUM_NAMING_GUIDE_WIKI.md)

**Concrete cross-platform Button API comparison (verified in source, Nov 2026)**

| System | Web | iOS (SwiftUI) | Android (Compose) |
|---|---|---|---|
| Backpack (Skyscanner) | (web repo archived; internal) | `BPKButton(…, size: BPKButton.Size = .default)` + `.buttonStyle(BPKButton.Style)`; `Style`: primary, secondary, destructive, featured, link, primaryOnDark, primaryOnLight, secondaryOnDark, secondaryOnContrast, linkOnDark; `Size`: default, large | `BpkButton(…, size: BpkButtonSize = Default, type: BpkButtonType = Primary)`; `BpkButtonType`: Primary, Secondary, Featured, PrimaryOnDark, PrimaryOnLight, SecondaryOnDark, SecondaryOnContrast, Destructive, Link, LinkOnDark; `BpkButtonSize`: Default, Large |
| Orbit (Kiwi.com) | `<Button type= size=>`; `Type` = "primary" \| "secondary" \| "critical" \| "primarySubtle" \| "criticalSubtle" \| "white" \| "bundleBasic" \| "bundleMedium" \| "bundleTop" | `Button(…)` with `enum ButtonType { primary, primarySubtle, secondary, critical, criticalSubtle, prominent, status(Status?, isSubtle:) }` | One function per variant: `ButtonPrimary`, `ButtonPrimarySubtle`, `ButtonSecondary`, `ButtonCritical`, `ButtonCriticalSubtle`, `ButtonBundleBasic/Medium/Top` |

- In Backpack, the variant values match one-for-one across iOS and Android (same 10 values, platform casing). The parameter name does not: iOS uses `style` (a SwiftUI-idiomatic modifier), Android uses `type`. — sources above
- In Orbit, the variant sets differ by platform (web has `white` and bundle types, iOS has `prominent` and `status(...)`, Compose has bundles but no prominent). The API shape differs too: an enum prop on web and iOS, separate composables on Android. — sources above
- Directory names of Backpack components drift between iOS and Android: `GraphicPromo` vs `graphicpromotion`, `Radio` vs `radiobutton`, `Swap` vs `swapbutton`, `NavigationTab` vs `navigationtabgroup`, `HorizontalNavigation` vs `horizontalnav`, `MapMarker` vs `map`. — [backpack-ios tree](https://github.com/Skyscanner/backpack-ios/tree/main/Backpack-SwiftUI); [backpack-android compose tree](https://github.com/Skyscanner/backpack-android/tree/main/backpack-compose/src/main/kotlin/net/skyscanner/backpack/compose)

**Other approaches**
- Wealthfront aimed for a "cohesive API on all platforms, ideally identical". Its naming rules: use a widely accepted name if one maps across platforms, otherwise avoid platform-specific names, but keep platform-unique ones (`Dialog` vs `BottomSheet`). Generic slots consistently use a `…Content` suffix (`primaryContent`, `helperContent`, `trailingContent`). It avoided `key` as a prop name because React reserves it. Per-component process: design component sheet (tokens, variants), engineering API proposal with alternatives, prototype on at least one platform, then build with unit, screenshot and screen reader tests. — [Wealthfront Engineering, May 2022 (old)](https://eng.wealthfront.com/2022/05/10/building-wealthfronts-multi-platform-design-system/)
- Spotify Encore pools iOS, Android and Web audits into one component "outline" covering terms, anatomy, variants and states. It shares a button hierarchy (primary/secondary/tertiary), a size framework and a naming structure across platforms. — [designsystems.com (Spotify)](https://designsystems.com/how-spotifys-design-system-goes-beyond-platforms/)
- Nathan Curtis (July 28, 2026): a component *contract* "centralizes design intent in one place so that it can be implemented, verified and evolved across implementations". React, iOS, Android, Web Components and Figma are all parties to it, and no platform owns it. "A description informs. A contract arbitrates." The schema is platform-neutral (e.g. `start`/`end` rather than `left`/`right`). An enum prop has name, options and default (e.g. `size`: small/medium/large, default medium). Deterministic scripts generate about 80–90% of component code (CSS, stories, TS contracts, scaffolds) before agents do the rest. Regenerating unchanged input should give an empty diff. ADRs drive schema versions. Machines verify structure (reject unknown props), and "Reading is review, not verification." — [Curtis: Component Contracts and Schemas](https://nathanacurtis.substack.com/p/component-contracts-and-schemas)
- Curtis also describes specs as managed over time (redesigns, platform builds, after release) rather than handed off once. He notes that a 3-platform setup (iOS, Android, web) is common and that Carbon spans many more. — [Curtis: Component Specifications](https://nathanacurtis.substack.com/p/component-specifications-1492ca4c94c); [Detach 2023 talk deck](https://speakerdeck.com/nathanacurtis/designing-and-automating-component-specifications)
- Airbnb's Lona (old) tried one cross-platform `.component` data format with a GUI editor and a compiler generating Swift (iOS/macOS), React DOM and React Native, with Kotlin planned. The repo (`Lona/Lona`) has had no push since Jan 2023. — [Lona repo](https://github.com/airbnb/lona); [Lona background doc](https://www.github.com/vldmrkl/Lona/blob/master/docs/overview/background.md)

### Inferences
- In practice, parity sits at the level of variant value names (e.g. `primary`/`secondary`/`destructive`, `default`/`large`). Parameter names and API shapes follow platform idiom: SwiftUI modifiers and enums, Compose parameters or separate composables, React props. A realistic rule for westron: identical concept and value names in the spec, idiomatic API shape per platform, with the mapping recorded in a machine-readable table (as in Spectrum's `implementations/` rows).
- Spectrum's `componentAliases` plus `namingExceptions` plus a CI drift-diff is the most concrete public pattern for allowed and recorded divergence. It is small enough to copy as a single `manifest.json` per platform.
- Curtis's "deterministic generation, then agent" workflow suits a one-developer-plus-AI team well. Keep a spec/contract file per component (props, variants, anatomy, states, tokens), generate scaffolds and tests per platform, and let the agent fill in behavior.

### Gaps
- I found no public, side-by-side cross-platform API table published by Fluent, Material or Carbon. Fluent's per-platform component pages exist but I did not extract their prop tables.
- I could not verify whether Spectrum's component-schema JSON files (e.g. `button.json`) list per-platform props. The path in `packages/component-schemas` did not resolve in my API call.

## Q3. How do systems document allowed platform divergence, and which components exist on only one platform?

### Takeaway
The common rule is: brand foundations (color, type scale, icons, voice) are shared, while navigation, system controls and interaction follow platform conventions (Apple HIG and Material). Systems record divergence as platform-specific packages, aliases and documented exceptions. Every system with native libraries has components that exist on only one platform.

### Cited Findings
- Primer mobile: "Android follows Material Design, and iOS and iPadOS follow Apple's Human Interface Guidelines". Shared across both are Octicons (16 and 24 px), an 8-point grid and a generated color system. — [primer.style/mobile](https://primer.style/mobile)
- Spotify Encore: shared foundations, button hierarchy and sizes. Each platform keeps "its own characteristics", and the design accounts for screen size and input type (desktop space, TV distance, Watch). The stated goal is "the pursuit of cohesion" between perfect consistency and total independence. — [designsystems.com](https://designsystems.com/how-spotifys-design-system-goes-beyond-platforms/)
- Wealthfront: `Dialog` (centered, desktop web) and `BottomSheet` (mobile) share padding, radius, color and type tokens, while positioning follows platform convention. `SummaryList` has a column option only for larger screens. For tap targets they "pick the largest minimum" across platforms. — [Wealthfront (2022, old)](https://eng.wealthfront.com/2022/05/10/building-wealthfronts-multi-platform-design-system/)
- EightShapes (Nathan Curtis) describes a team spanning web, iOS and Android whose single icon library ran into Android designers' pushback, because Android already has established icons for many concepts. The team built a parallel Android set. (From the search snippet; the article itself returned HTTP 500.) — [EightShapes: Finding platform balance in a design system](https://eightshapes.com/articles/finding-platform-balance-in-a-design-system/)
- Spectrum handles divergence in data: `componentAliases` (`button`→`button-ios`, `switch`→`switch-ios`), `platform-extensions/` for platform names of existing registry entries (it "cannot add new ids"), `modeSetRestrictions`, and `extensions/visuals/` for per-platform visual recipes. — [Spectrum manifest spec](https://opensource.adobe.com/spectrum-design-data/spec/manifest); [ios manifest](https://github.com/adobe/spectrum-design-data/blob/main/platforms/ios/manifest.json)
- Backpack foundations split tokens into `common/base` ("consistent across all platforms, like colours or animations"), `common/app` ("shared across iOS and Android") and platform packages for tokens "only applicable to them, e.g. breakpoints for web or elevations for Android". — [backpack-foundations README](https://github.com/Skyscanner/backpack-foundations)
- Components present on only one Backpack platform (by directory, Nov 2026): Android Compose only has `barchart`, `bottomnav`, `fab`, `flightleg`, `floatingnotification`, `modal`, `divider`, `dividedcard`, `cardwrapper`. iOS SwiftUI only has `CarouselCard`, `DynamicLayout`, `FlowStackView`, `IntentTriggerButton`, `TappableContainer` and `Shaders`. — [backpack-ios](https://github.com/Skyscanner/backpack-ios/tree/main/Backpack-SwiftUI); [backpack-android](https://github.com/Skyscanner/backpack-android/tree/main/backpack-compose/src/main/kotlin/net/skyscanner/backpack/compose)
- Fluent Apple's component set includes Microsoft-365-mobile-specific controls with no direct web equivalent: `BottomCommanding`, `PillButtonBar`, `PersonaButtonCarousel`, `EasyTapButton`, `TwoLineTitleView`, `ResizingHandleView`, `TouchForwardingView`. Fluent Android ships separate Gradle modules (`fluentui_ccb` contextual command bar, `fluentui_drawer`, `fluentui_peoplepicker`, `fluentui_persona`, `fluentui_topappbars`, `fluentui_transients` and others). — [fluentui-apple Sources](https://github.com/microsoft/fluentui-apple/tree/main/Sources); [fluentui-android](https://github.com/microsoft/fluentui-android)
- DuckDuckGo's `DesignResourcesKit` (iOS and macOS, colors and typography only) allows content changes "only if the changes are applied across the design system". It has an explicit escape hatch, `SingleUseColor`, for one-off colors, and you should "think carefully before adding a color here". The package now lives in the `duckduckgo/apple-browsers` monorepo. — [DesignResourcesKit README](https://github.com/duckduckgo/DesignResourcesKit)
- Other commonly cited platform-only components are iOS share extensions and the Android FAB (secondary source). — [designsystemproblems.pages.dev](https://designsystemproblems.pages.dev/cross-platform-consistency/multi-platform-components)

### Inferences
- A good pattern for westron: a per-component "platform support" field in the spec (`apple: native-control | custom | n/a`, `web: …`, `linux: …`) plus a rule that system controls (navigation stacks, tab bars, menus, pickers, sheets on Apple) use the native SwiftUI control styled through tokens instead of being reimplemented.
- An explicit escape hatch like DuckDuckGo's `SingleUseColor` or Spectrum's `namingExceptions` is cheaper and more honest than pretending to have 100% parity.

### Gaps
- I did not find an official written "Fluent vs HIG" divergence policy page. Fluent's per-platform docs exist, but I did not extract a policy statement.
- No public Material 3 guidance for adapting to iOS was found. Google has withdrawn from iOS.

## Q4. Small-team and open-source systems covering SwiftUI + web + Android: repo structure, specs, maintainers

### Takeaway
The open multi-platform systems that survive use one repo per platform plus a shared foundations/tokens repo published to npm, which native repos consume at build time and turn into code. Several notable open systems closed their native repos in 2025–2026 (Orbit native, Mistica native, Backpack web, Thumbprint, Primer mobile). This suggests that even well-funded companies find open-sourcing several native libraries hard to sustain.

### Cited Findings

**Skyscanner Backpack (still the most complete open SwiftUI + Compose system)**
- Repos (Nov 2026): `backpack-ios` (Swift, active), `backpack-android` (Kotlin, active), `backpack-foundations` (tokens monorepo, lerna), `bpk-svgs` (icons), `eslint-plugin-backpack`, `stylelint-plugin-backpack`. Archived: `backpack` (web, Aug 2026), `backpack-react-native` (Dec 2024), `backpack-docs` (2023), `backpack-swiftlint-rules` (2023), `figma-backpack` (2023). — GitHub API search of [Skyscanner org](https://github.com/Skyscanner)

- `backpack-foundations/packages` contains `bpk-foundations-common`, `-ios`, `-android` and `-web`. Platform packages inherit common tokens and re-export them through `aliases.json`. Consumers should not install the common package directly. — [backpack-foundations README](https://github.com/Skyscanner/backpack-foundations)

### Inferences
- The repo pattern most worth copying for westron is Backpack's: one foundations package (common/base, common/app, per-platform) generated from a single token source, plus native repos that consume it at build time and generate code from templates. - The wave of native repos going private or archived (Orbit 2025, Mistica native, Primer mobile, Backpack web 2026) means few current, maintained open SwiftUI design systems remain to learn from. Backpack-SwiftUI, fluentui-apple and GOV.UK `mobile-ios-ui` are the main live references.

- I found no public reason for Kiwi.com archiving the Orbit native libraries.
- Bitwarden's, Proton's and Signal's internal UI-kit structures were not examined in depth.

## Q5. Published post-mortems and lessons learned

### Takeaway
The recurring failure modes are: (1) shared cross-platform UI code that falls out of sync with native or is too costly to keep up (Airbnb React Native, Lona); (2) gradual drift and over-flexibility between platform libraries (Spotify's 2022 "swung too far towards flexibility"); (3) token or override pipelines that nothing validates (Spectrum iOS's CSV merge); and (4) vendors cutting back to fewer libraries (Material iOS, Views and web; spectrum-css; polaris-react). What works is measured adoption and drift (Uber), CI-validated data contracts (Spectrum) and cross-platform component reviews (Spotify, Snapp).

### Cited Findings
- Spotify: before the cross-platform work, buttons "varied widely across platforms" in size framework, padding and type increments. By 2022 the system had "swung too far towards flexibility". The cross-platform work raised project complexity and dependencies, mitigated by limiting active projects. Advice: "Unity is invaluable", so define non-negotiables. — [designsystems.com (Spotify)](https://designsystems.com/how-spotifys-design-system-goes-beyond-platforms/)
- Airbnb: native and React Native versions of the same component would get out of sync and fragment. Airbnb chose to rewrite components rather than wrap native ones (2018, old). — [Airbnb: React Native at Airbnb: The Technology](https://medium.com/airbnb-engineering/dafd0b43838)
- Lona, Airbnb's attempt at a single cross-platform component spec compiled to Swift and React, stalled at "developer preview". No push since Jan 2023. — [Lona repo](https://github.com/airbnb/lona)
- Adobe's own critique of Spectrum iOS: "Nothing validates overrides against the foundation", "Foundation bumps break overrides silently", and "Figma↔code is one-way, manual, token-by-token". The fix is a declarative manifest plus CI drift diff. Adobe also corrected its strategy doc because an earlier design (inline TOML filters, per-platform generated SDKs, UniFFI/JNI bindings) "was **never built**". — [SDK strategy doc](https://github.com/adobe/spectrum-design-data/blob/main/SPECTRUM_MULTIPLATFORM_SDK_STRATEGY.md)
- Uber: degradation usually comes from missing guardrails, and "the earlier an issue is caught … the fewer days it takes to fix it". Teams need "a shared and trackable OKR". — [Uber blog (2024)](https://www.uber.com/blog/design-system-at-scale/)
- Wealthfront: stepping back from platform specifics exposed needless duplication (separate web `Button` and `Link`). Web cannot restrict child component types at compile time, so some constraints became runtime checks in dev builds only. Tying the design system to a product refresh "can be a recipe for disaster" but helped adoption. — [Wealthfront (2022, old)](https://eng.wealthfront.com/2022/05/10/building-wealthfronts-multi-platform-design-system/)
- Snapp Mobile: feature parity is hard to keep up and teams slip into a "platform silo mentality". Their fix: iOS developers demo the Android implementation and vice versa. — [Snapp Mobile: Why multi-platform is hard](https://medium.com/snapp-mobile/why-multi-platform-is-hard-and-what-you-can-do-about-it-5e76e16a1bf5)
- Vendor retrenchment as evidence of maintenance cost: MDC-iOS maintenance (2021), MDC-Android Views maintenance (I/O 2026), MWC "maintenance mode pending new maintainers", Flutter Material/Cupertino frozen and decoupled (Apr 2026), spectrum-css archived, polaris-react archived, Fluent token pipeline archived (2024). — [MDC-iOS](https://github.com/material-components/material-components-ios); [MDC-Android](https://github.com/material-components/material-components-android); [MWC](https://github.com/material-components/material-web); [Flutter](https://flutter.dev/blog/flutters-material-and-cupertino-code-freeze); [spectrum-css](https://github.com/adobe/spectrum-css); [polaris-react-archive](https://github.com/Shopify/polaris-react-archive); [fluentui-token-pipeline](https://github.com/microsoft/fluentui-token-pipeline)
- Practitioner claim (vendor blog, lower reliability): drift between platforms can happen "within two release cycles" with a shared master file. — [Flatstudio](https://www.flatstudio.co/blog/two-figma-files-one-brand-library-how-we-kept-statkings-ios-and-web-apps-visually-identical)

### Inferences
- For a solo developer, the main risks are maintaining more platform libraries and bindings than one person can sustain, and silent drift. Mitigations: keep shared data in one machine-validated source, generate as much as possible, use snapshot and screenshot tests per platform, and add a cheap drift check (e.g. a CI script comparing each platform's exported component/variant inventory with the spec).
- Shared runtime UI code across Apple, web and Android has a poor track record in published accounts. Sharing data (tokens, specs, icons, content) is the consistently recommended boundary, which matches westron's "cross-platform core + native UI" plan.

### Gaps
- I found no recent (2025–2026) formal post-mortem from a major vendor specifically about multi-platform design-system failure. Most lessons are older blog posts or implicit in archive notices.
- I found no public account from teams using Compose Multiplatform or Kotlin Multiplatform for shared design-system UI on iOS.

## Q6. Typical layering model and how versioning and releases are coordinated across platforms

### Takeaway
Layering is converging on: platform-neutral foundation data (tokens, color algorithms, schemas, icons) → per-platform token build/overrides → native primitives and components → patterns, with product-level overrides on top. Releases are decoupled. Foundations are versioned and published once (npm, a tagged release), and each platform library pins a foundation version and releases on its own semver cadence. Adobe adds CI drift detection between the pin and the latest foundation.

### Cited Findings
- Spectrum cascade: Layer 1 foundation schemas (cannot be overridden) → Layer 2 platform `manifest.json` (pin, filters, overrides, extensions) → Layer 3 product context. Precedence is `Foundation < Platform < Product`. Platforms pin with `foundationVersion` (canonical tag `@adobe/spectrum-design-data@<version>`). The iOS pipeline planned to move from `@adobe/spectrum-tokens@13.0.0` to a cascade-format release (`15.0.0`+). — [manifest spec](https://opensource.adobe.com/spectrum-design-data/spec/manifest); [SDK strategy doc](https://github.com/adobe/spectrum-design-data/blob/main/SPECTRUM_MULTIPLATFORM_SDK_STRATEGY.md)
- Adobe's three-role ownership model: Foundation (core team: dataset + SDK), Platform manifest repo (platform design/eng: declarative overrides + CI + AI config), Platform implementation (native library + its code generator, "fed by a resolved dataset rather than a bespoke merge"). Platform manifests first incubate inside the monorepo under `platforms/<id>/` and can be split out with `git subtree split` "with zero required changes for any consumer". — [SDK strategy doc](https://github.com/adobe/spectrum-design-data/blob/main/SPECTRUM_MULTIPLATFORM_SDK_STRATEGY.md); [platforms/README.md](https://github.com/adobe/spectrum-design-data/blob/main/platforms/README.md)
- Backpack: `bpk-foundations-common` (base for all platforms, app for iOS+Android) → `bpk-foundations-{ios,android,web}` on npm → native repos consume via npm and generate code → components. Each native repo keeps its own `CHANGELOG.md`. — [backpack-foundations](https://github.com/Skyscanner/backpack-foundations); [backpack-ios](https://github.com/Skyscanner/backpack-ios)
- Spotify Encore: Encore Foundation (tokens) → Encore Web / Encore Consumer Mobile, with a reusable-mobile-component layer added in between around 2022 → local, platform- and audience-specific systems. — [designsystems.com (Spotify)](https://designsystems.com/how-spotifys-design-system-goes-beyond-platforms/)
- Primer primitives are split into `base` and `functional` token tiers (e.g. `base/size/size.css` vs `functional/size/border.css`) and distributed via npm `@primer/primitives`. — [primer/primitives README](https://github.com/primer/primitives)
- SLDS 2 has two tiers of styling hooks: global (supported, including semantic UI color hooks) and component-level `--slds-c-*` (not supported in SLDS 2). — [Salesforce dev docs](https://developer.salesforce.com/docs/platform/lwc/guide/create-components-css-slds1-slds2.html)
- Fluent Apple is consumed via SPM with `.upToNextMinor(from:)`, which signals that minor releases may break. — [fluentui-apple README](https://github.com/microsoft/fluentui-apple)
- Polaris versions its web components with dated API versions (`2025-10`). The admin signals which styling version to load via App Bridge, so apps built only from Polaris web components get the 2.0 visuals without code changes. — [shopify.dev stable changelog](https://shopify.dev/changelog/polaris-unified-web-components-are-now-stable); [Polaris 2.0 RC](https://shopify.dev/changelog/posts/polaris-2-0-release-candidate)
- Wealthfront's color pipeline (old): an algorithm turns a few brand colors into an accessible theme, a script checks contrast for common pairs, and outputs are Android XML, iOS JSON and web CSS variables, with nested theming per subtree or component. — [Wealthfront (2022)](https://eng.wealthfront.com/2022/05/10/building-wealthfronts-multi-platform-design-system/)
- Tooling commonly used for the foundation-to-platform step: Style Dictionary (`style-dictionary/style-dictionary`, active Nov 2026) and the DTCG format (`design-tokens/community-group`, active). Spectrum emits DTCG via `resolve --format dtcg`. — [style-dictionary](https://github.com/style-dictionary/style-dictionary); [DTCG repo](https://github.com/design-tokens/community-group); [SDK strategy doc](https://github.com/adobe/spectrum-design-data/blob/main/SPECTRUM_MULTIPLATFORM_SDK_STRATEGY.md)

### Inferences
- A layering for westron that matches current practice: (0) foundation data (DTCG JSON tokens with primitive → semantic tiers, icons, component spec/contract files with variants, states and anatomy) → (1) per-platform generated tokens (Swift `Color`/`Font` extensions or asset catalogs, CSS custom properties, later Compose `Color`/`Typography`) with an optional platform manifest for overrides and aliases → (2) native primitives (Text, Icon, Surface/Stack) → (3) components → (4) patterns and app templates.
- Versioning for one developer: one foundation semver. Each platform package pins it, and CI fails when a platform falls behind or when its component inventory diverges from the spec. Spectrum's `diff`-style drift gate can be recreated with a small script.

### Gaps
- I did not verify the current DTCG specification version and status (stable vs draft) from primary sources this session.
- How Fluent coordinates releases across fluentui-apple, fluentui-android and React v9 (shared changelog or independent cadence) is not documented publicly in what I found.
